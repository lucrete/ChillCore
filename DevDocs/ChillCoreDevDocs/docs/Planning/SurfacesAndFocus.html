Surfaces and Focus

The UI now serves the desktop window and any number of panels standing in the world at once. What that changed, what it fixed, and the plan for input and pause that follows from it.

Feature brief

Intended behaviour. The sections after this one record work in progress and are partly out of date; where they disagree, this brief holds.

Where the app runs

  • Desktop — keyboard, mouse, gamepad.
  • Touch device — tablet or phone. Touch only; attached keyboards and gamepads are not supported.
  • XR on desktop — headset and two controllers driven by a desktop. The desktop window shows the headset view.
  • Standalone XR — headset and two controllers with nothing else attached. No desktop window, no keyboard.

Behaviour below marked XR applies to both XR forms unless it names the desktop window or keyboard, which exist only for XR on desktop.

Starting

  • XR on desktop: with a headset present at launch, the app starts in XR. A headset connected later can be entered from the pause menu.
  • Touch controls show from the start on a touch device.

Playing

  • Desktop — mouse, keyboard and gamepad move and look. The on-screen display shows information only; it has no controls.
  • Touch — on-screen sticks move and look. An on-screen button pauses.
    • The touch controls are always shown during play.
  • XR — the head looks. The controllers point at, touch and grab things in the world.
    • Things in the world are of two kinds:
      • Simulation objects — part of the world that runs. Touched and grabbed.
      • Interface objects — panels and three-dimensional controls. Pointed at from a distance, or touched directly.
    • Interface objects respond to whichever hand reaches them, and two hands can use one at once.

Pausing

  • Triggers
    • Desktop: Escape, or Start on a gamepad.
    • Touch: the on-screen pause button.
    • XR: the A button on the right controller. On XR on desktop, the desktop keyboard also pauses.
  • The world freezes in place. It stays visible.
    • Each part of the world is either paused or continues through a pause. Most of it pauses.
    • Ambient effects may continue — the AppState decides per effect, so a paused scene can still feel alive.
  • Desktop and touch — a pause menu replaces the on-screen display. The cursor is free.
  • XR
    • A pause panel appears in front of the head, wherever the player is looking.
    • Head tracking continues. The view never stops following the head.
    • Controllers can point at or touch the pause panel.
    • Simulation objects that pause cannot be touched or grabbed until the world resumes.
    • The AppState's own interface objects stop responding. Whether they also hide depends on what the AppState is doing.
    • XR on desktop only: the desktop window keeps the headset view and shows its own pause menu over it. The desktop menu and the headset panel are different screens. Neither mirrors the other, and either one can resume.
    • Standalone XR: the pause panel is the only menu. The A button that paused also resumes.
  • Resuming returns to exactly what was there before: the same controls, the same screen, the same cursor capture.

AppStates without a pause

  • Pausing is a choice each AppState makes. An AppState with no world to freeze — the audio tracker — has no pause and no pause control.
  • Switching AppStates discards any pause. The incoming AppState starts running, with its own controls.

Input goes where it is meant

  • While a menu is up, input drives the menu and nothing moves in the world.
  • While playing, input drives the world and never moves a selection in a hidden or display-only menu.
  • A control that is drawn always responds. A control that should not respond is not drawn, or is visibly inactive.

Tech brief

Implementation plan for the feature brief. XR session lifecycle across AppStates is out of scope for this plan.

Kept as is

  • Touch controls — shown from the start on Android builds, then shown or hidden as touch becomes or stops being the input in use.
  • XR at launch — a headset found at startup starts a session before the first frame.

1 · World pause and the Simulation clock

  • Pause mechanism unchanged
    • SceneHierarchy holds one scene-wide pause flag. No per-object or per-subtree pause.
    • Components opt in with SetPauseable(true). A paused component's Update is skipped.
    • Renderables stay non-pauseable, so a paused scene keeps drawing.
  • Simulation clock in FrameTimer
    • Simulation delta and Simulation elapsed time, alongside real time.
    • Time scale. Pausing stops the Simulation clock.
  • Which clock a component reads
    • Pauseable components read Simulation time. Resuming continues from where they stopped rather than jumping.
    • Non-pauseable components read real time and ignore the time scale.
    • Fixed by the pause setting; never switched at runtime.
    • Moves RotateRandom and the Showcase quad animation off TimeSinceStartup.
  • Shaders
    • timeAbsolute stays in the frame block and is fed Simulation time. No shader changes.
    • The CPU wraps the value to hold float precision over long sessions. Period to be chosen.
    • A material that must animate through pause passes real time through its own material uniform.
  • The pause flag and the Simulation clock stay two facts, set together by the AppState base (topic 4).

2 · Actions per channel, every device read

  • Pausing the Simulation is AppState state, not input. The action map knows nothing of pause.
  • Distinct actions per channel
    • Window actions bind gamepad-style triggers, which keyboard, gamepad and touch already share. Headset actions bind XR triggers.
    • Example: Pause on GamepadStart (Escape maps to it), PauseXr on XrPrimaryRight (the A button).
    • The channel an action came from is carried by which action fired. No separate origin mechanism.
    • One trigger per action, unchanged. Code that does not care about the channel checks both actions.
  • Every device read every frame
    • Keyboard, gamepad and XR triggers are all evaluated each frame. An action fires from its own device whatever the active input type is.
    • Active input type is kept only for touch control visibility, per-device camera speeds and future visual prompts.
  • Stick directions as navigation triggers
    • Window navigation triggers gain gamepad D-pad and gamepad stick directions alongside the arrow keys. A trigger already accepts several physical inputs, and axis-past-threshold is already supported in both directions.
    • New XR triggers for thumbstick directions, pushed from XrInput past a threshold, bound to Headset navigation actions.
  • Analog values stay direct reads. Movement and look are not actions.
  • Open
    • Which gamepad stick navigates: left only, or both.
    • Hold-to-repeat for navigation; today navigation fires on the press edge only.
    • Threshold and release hysteresis for stick directions, so a stick resting near the threshold does not flicker.
    • The free camera's move actions also bind the D-pad. Resolved by input targets: the camera reads only under a Scene target and navigation only under a Surface target, so the two never overlap.

3 · Input domains and input targets

  • InputDomain — a group of devices with one consumer at a time.
    • Window — keyboard, mouse, gamepad, touch. Everything arriving through the platform.
    • Headset — XR controllers. Everything arriving through OpenXR.
    • Head tracking belongs to neither. It always drives the XR camera.
    • A standalone headset has no Window domain in practice; a touch device or a desktop without XR has no Headset domain.
  • Input target — each domain has exactly one: InputTargetScene or InputTargetSurface naming one surface.
  • What a target gates
    • Window + Scene — the camera reads mouse and sticks directly; the cursor may lock. The window surface takes no pointers.
    • Window + Surface — that surface takes pointers and Window navigation actions; every element on its current screen is reachable. The camera does not read devices.
    • Headset + Scene — rays and touch reach simulation objects and the AppState's interface objects; grab is live.
    • Headset + Surface — rays and touch reach that surface only; no grab.
  • Camera rule — replaces IsWorldInteractable. Read devices directly only while the Window target is Scene. Always read touch-stick values; they exist only when a surface holding the target set them.
  • Targets per case
    • Desktop play — Window Scene.
    • Touch play — Window Surface (HUD). Fixed; touch devices take no peripherals.
    • Desktop or touch pause — Window Surface (pause menu).
    • XR play — Window Surface (window HUD), Headset Scene.
    • XR pause — Window Surface (desktop pause menu), Headset Surface (pause panel).
  • The mirror window takes a Surface target, not Scene. A click gives the window OS focus whatever the application does with it; the desktop HUD has nothing clickable, so the click is absorbed and Escape then pauses. Under Scene the same click would lock the cursor into a window the player cannot see.
  • Removed — the per-element world-focus opt-in. A Surface target makes every element on the screen reachable, and the screen shown decides what exists to press.
  • The AppState sets its targets directly (topic 4).

4 · Pausing an AppState

  • No mode abstraction. One base class, StateMachineState, holds what is truly common. Everything per-AppState lives in the derived AppState.
  • Base class
    • isPausable — protected, false by default, set by the derived AppState like isXrSupported.
    • IsPausable(), IsPaused().
    • SetPaused(bool) and TogglePause() — non-virtual. Assert the AppState is pausable, act only on a change, set the scene pause flag and the Simulation clock, then call OnPaused() or OnResumed().
    • OnPaused(), OnResumed() — protected virtuals, empty by default.
  • Derived AppState, in OnPaused and OnResumed
    • Action-map context. Contexts are created and named per AppState; UI navigation and developer actions are added to every context by the engine.
    • Window and Headset input targets.
    • Window screen swap between its HUD and the pause menu.
    • Show and hide the XR pause panel. The panel places itself in front of the head when shown.
    • Its own world panels: non-interactive, and hidden if it chooses.
  • Triggering — the AppState polls its own Pause and PauseXr actions, and wires its touch pause button, then calls TogglePause().
  • Resuming is a flat switch. No stack. Each AppState restores what it changed.
  • Cursor lock follows the Window target. A Surface target frees it; a Scene target restores what it was before. Removes the per-AppState wasMouseLocked copies.
  • Leaving a paused AppState — StateMachine resets the global parts during the swap without calling the leaving AppState: scene pause flag cleared, Simulation clock running, input targets to their defaults. OnResumed is not called; the leaving AppState's screens and panels are destroyed by its own Shutdown.

5 · XR hands: pointing and grabbing

  • Engine-owned. Moves out of AppStateXrDemo, so every XR AppState gets both without per-AppState code.
  • Pointing
    • An engine XR hand system submits both aim rays every frame, whatever the pause state; draws the rays; pulses a haptic as a ray moves onto an interface object.
    • The pointer router filters by the Headset target: Scene offers rays to every registered target, Surface offers them to that surface only.
  • Grabbing
    • Grabbable objects register with the engine, as panels register with the router.
    • Grab is live only while the Headset target is Scene. Under a Surface target nothing is grabbable, including simulation objects that continue through a pause.
    • When the Headset target leaves Scene, every held object is released where it visibly is, as an ordinary release. Resuming does not re-attach it.
  • Pause panel placement
    • Placed once, when shown, in front of the head along its yaw. It does not follow the head afterwards.
    • Vertical, facing the player. Centred at head height, 1 m in front of the head along its yaw.
    • Pause panel only. Every other world panel keeps the fixed placement its scene gives it.
  • Interface objects are ray-only in this plan.
  • Future work — direct touch
    • A contact test at the fingertip or controller tip alongside the ray test.
    • Press by pushing past a depth, with release hysteresis.
    • Touch outranks the ray for the same hand.

6 · Removals

  • InteractionMode, SetInteractionMode, GetEffectiveInteractionMode — replaced by input targets.
  • IsWorldInteractable, IsUiInteractable, IsHudInteractable — replaced by the camera rule and a surface asking whether it holds the target.
  • InputManager::SetPaused, IsPaused — pause is AppState state.
  • The world-focus opt-in: SetWorldFocusReachable, the UiJoystick default, the hit test's isWorldFocusOnly parameter.
  • Per-AppState wasMouseLocked copies — the cursor follows the Window target.
  • AppStateXrDemo hand code — UpdateHands, UpdateGrab, UpdateRay, SubmitPanelPointer — moves to the engine.
  • StateMachine::ExecuteStateSwap resets input targets to their defaults in place of InputManager::SetPaused(false). The scene pause and Simulation clock reset stay.
  • Bridge, kept — SetXrOwnsInput. A running session sets the Window target to the window surface, standing in for the XR lifecycle work. Removed with that work.
  • The Showcase HUD's tracking label reads the XR session rather than an interaction mode of None.

Objective

Why the work was scheduled ahead of XR.

UiManager held one root element, one id map, one layout cache and one input handler. UiScreenSystem held one screen stack. Loading a screen replaced the tree.

Every awkward thing in the XR work traced to that:

  • A pointer laid out against one surface hit-testing against another.
  • A panel blanked so the desktop menu could have the slot.
  • A “current surface” that nothing declared.

The objective was one surface per destination, so the in-headset panel and the desktop pause menu coexist instead of taking turns.

The surface model

A surface is one root element, one id map, one stylesheet, one layout state, one size, one screen stack and its pointers.

  • window surface
  • panel surface
  • world / scene

Delivered in five steps

  1. U1

    Extract the surface

    Per-surface state out of UiManager into UiSurface. UiScreenSystem stops being a singleton and becomes one per surface. Controllers bind to their surface at registration and never rebind.

  2. U2

    Surfaces on request

    Creation and destruction on demand. The engine owns the window's surface from startup. Where no window exists, it returns a surface that is real and has nothing behind it, so application code never branches on the target.

  3. U3

    Several pointers

    Each pointer keeps its own hover and press, so a press stays with the hand that began it. Element state is derived across all of them. Android multi-touch stopped being a special path — the mouse is pointer zero and fingers take the slots above it.

  4. U4

    Panels in the world

    UiWorldPanel is a scene component, factory-registered so panels are authorable in scene files. A router resolves world rays to hit-testable targets. GPU scopes are named UI/<surface>.

  5. U5

    Redraw on change

    Marking is automatic — in the element setters and in the input handler's hover and press transitions. A panel nobody is pointing at submits no work at all.

Decisions settled

Recorded so the reasoning outlives the diff.

Yours

Screen stacks belong to the scene

A state registers the screens it uses — including sub-screens its menus route to — and clears them on exit. Registering shared screens once at application startup was tried and reverted: it splits ownership of one registry, so a state's clear on exit destroys screens it never registered.

Yours

Each state declares whether it supports XR

A flag on StateMachineState, false by default. The pause menu offers the XR entry only where the state supports it. A state authored for a window has not thought about stereo, a tracked head or a scene in metres — the AudioTracker is the clear case.

Yours

A state swap is independent of restoring the cursor lock

Unpausing is a return: the same scene resumes, so the cursor goes back to what the player had. A state swap is a discard: the outgoing scene's cursor state means nothing to the incoming one, which sets its own in Init.

Mechanism changes with tech brief 3 and 4. The principle stands; the cursor now follows the Window input target, and a swap resets the targets rather than restoring a saved lock.

Already documented, violated in code

Pause is a component property, not a disabled hierarchy

AGD-0020 already said it: renderables submit themselves during their update, so disabling the hierarchy makes the scene disappear rather than freeze. The XR demo was the one place using SetEnabled, which is why the window went blank behind the menu.

Mine, flagged — superseded

World-focus reachability is a per-element opt-in

A heads-up display is drawn over a scene the pointer also drives, so a click there is a camera look as much as a press. Elements are unreachable unless they say otherwise. This replaced a check on element type, under which every non-joystick control was silently inert — drawn, and pressed by nothing.

Superseded by tech brief 3. A Surface input target makes every element on the current screen reachable, so the opt-in is removed.
